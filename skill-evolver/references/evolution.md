# 进化模式设计：融合、评测与迭代回路

目标：不是简单挑第一名，而是把多个候选 skill 的优势融合成一个新 skill，并通过"执行同一任务 → 对比打分 → 定向迭代"，直到融合版稳定优于所有原始候选。

## 回路总览

```
任务解析 → GitHub 搜索筛选 → 提取融合(v0) → 执行任务 → 对比打分
                                    ↑                        │
                                    └── 差距分析 ← 未达标 ────┘
                                                             ↓ 达标
                                                     交付 skill + 进化报告
```

## 1. 任务解析（约占总精力 30%，评测集是系统的心脏）

- 输入：用户任务描述
- 输出：结构化任务卡
  - 任务目标 + 输入样例
  - 验收 checklist（可验证的判分标准，如"输出含 X 字段"、"耗时 < Y 秒"）
  - 评测任务集：≥ 3 个变体任务；迭代只用其中 2 个，留 1 个盲测防过拟合

## 2. 搜索筛选

- 输入：任务关键词
- 筛选标准：star ≥ 50（小众放宽 ≥ 20）、近 6 个月有 commit、LLM 相关性评分 ≥ 6/10、license 明确
- 输出：3-5 个候选仓库（太多稀释融合质量，太少失去对比意义）+ 元数据表

## 3. 提取融合

- 输入：各仓库 SKILL.md / README / 核心脚本
- 方法：提取每个 skill 的可组合优势片段（A 的检索策略 + B 的输出结构 + C 的错误重试）；冲突时以"哪个有验收证据"裁决；逐条标注来源
- 输出：v0 融合 skill（标准 skill 目录结构）

## 4. 执行与采集

- 同一评测任务集 ×（N 个原始 skill + 1 个融合版），沙箱执行
- 记录：结果产物、日志、耗时、token、错误/重试次数

## 5. 对比打分（评分矩阵）

| 维度 | 权重 | 判分方式 |
|------|------|----------|
| 准确性 | 0.40 | 优先客观判据（脚本断言、格式校验）；LLM judge 仅兜底 |
| 完整性 | 0.30 | 验收 checklist 覆盖率 |
| 效率 | 0.15 | 耗时 + token 归一化 |
| 稳健性 | 0.15 | 跨变体任务得分的方差 |

- 输出：评分矩阵（行=候选，列=任务×维度）+ 差距分析

## 6. 迭代

每轮只针对最弱项定向修改，不推倒重来；保留每轮 skill 版本与评分记录。

### 终止标准（满足任一即停）

1. **达标**：融合版连续 2 轮所有维度 ≥ 每个原始 skill，且加权总分领先最强原始 skill ≥ 10%
2. **上限**：5 轮迭代上限，交付当前最优 + 如实标注未达标项
3. **收益**：连续 2 轮总分提升 < 2%，边际收益消失

## 交付格式

```
<evolved-skill>/
├── SKILL.md          # frontmatter + 融合后的工作流
├── scripts/
├── references/
├── EVOLUTION.md      # 候选清单、评分矩阵、每轮迭代记录、来源与 license 标注
└── CHANGELOG.md      # 各版本差异与修改理由
```

## 三个红线

1. 验收标准写不出来就不启动进化——否则打分退化为 LLM 自评，系统性偏爱自己
2. 只在单任务上赢不算赢，必须过盲测变体
3. 交付物逐条标注代码来源与 license（GPL 需评估传染条款，无 license 仓库不融合）
